## 起因

上一篇写的是把一堆服务搬上服务器，dsh 只是“顺带搬上去的一个 AI 工具”，跑通 502 之后就一直吃灰。

这一周它才真正开始干活。起因很朴素：我想在自己的聊天软件里直接对它说话——想到什么就发一句，让它帮我记下来、排上日程、算清楚这个月花了多少钱。于是接了 QQ 和微信两个通道，把滴答清单和 Memos 两个 MCP 挂上，再把账本和播客这两件本来要靠人惦记的事交给定时任务。

折腾下来最大的感受是：**AI 真正省时间的不是它替你做决定，而是它替你记住该做的事，并且在你忘记之前把消息递到你手上。**

## 消息通道：QQ 和微信都接上了

dsh 自带 IM 插件，QQ 走腾讯官方 Bot API，微信走官方接口，各接一个账号、绑到我自己的 ID 上。

两条通道的分工是被使用习惯逼出来的：

| 通道 | 能发什么 | 现在主要负责 |
|---|---|---|
| QQ | 文字、图片、文件、视频 | 行情卡片、额度播报、播客报告 |
| 微信 | 仅文字 | 日常聊天、待办速览 |

现在常驻六个定时任务：

| 时间 | 任务 | 送达 |
|---|---|---|
| 每天 07:00 | 今日待办速览 | QQ + 微信 |
| 工作日 09:00 | 科创50 / 创业板指收盘卡片 | QQ（纯图片） |
| 每天 17:00 | OpenCode Go 额度播报 | QQ |
| 每天 23:00 | 当日对话记忆整理 | Memos |
| 每天 03:00 | 账本仓库同步 | QQ |
| 每周日 03:00 | 播客流水线巡检 | QQ |

每天早上那条速览是这一整套里用得最顺手的：它把滴答清单里今天到期和已经逾期的任务捞出来，再把前一天聊天里我口头答应过、但没做完的事补上——后一部分靠翻会话历史，是提醒机器自己补上的；最后再顺手看一眼三张卡的余额，低于阈值才提一句充值。不用打开任何 App，一条消息扫完。

## 两个 MCP：滴答清单和 Memos

消息进来之后得有个去处，所以给工作区写了一份规则（`AGENTS.md`，每轮自动注入）做分流：

- **待办 / 提醒** → 滴答清单（不指定清单时统一丢收集箱，不许自作主张分到“生活”“技术”里）；
- **备忘 / 随手记** → Memos（默认私有，不主动改成公开）；
- **提问 / 闲聊** → 直接回答，不往任何一边写。

另外加了一层“长期记忆协议”：我明确说“记住”、或者聊到一些长期有效的事（作息、偏好、项目背景），它就写进 Memos 里一个专门的“AI记忆”空间，格式是首行 `#记忆/<类别>`，下次需要时再捞出来用。这样换会话、换机器也不至于把习惯全丢了。

## 账本：复式记账 + 订阅 + 耗材

一直想做个人记账，试过几个 App 都不满意——要么要订阅，要么数据不在自己手里。最后决定用最笨的办法：纯文本复式账本。

仓库在 [book-keeping](https://github.com/TangMisaka23001/book-keeping)，结构很简单：

```
main.bean                 根文件：标题、币种、include 其他文件
accounts.bean             账户表：所有账户先在这里 open 才能用
transactions/2026-11.bean 交易：按月一个文件
subscriptions.md          订阅台账
consumables.md            耗材台账
tools/ledger.mjs          校验 + 报表
tools/build-site.mjs      生成静态展示页
```

核心原则只有一条：**每笔交易至少两条 posting，金额相加必须为 0**。账目自己就能验自己，AI 写错了也会被工具当场拦下来。机器上没装 beancount，就用自己写的 `tools/ledger.mjs` 查配平、查账户有没有 open、查缺金额，够日常用。

流程也守住了 AI 该有的规矩：它给出条目草案 → 我确认 → 写入当月文件 → 跑 `check` 必须通过。不确认不写，不改历史条目，同一笔只记一次。余额型支出（话费、订阅扣费）还要先确认余额和扣费日再记。

除了流水，还有两张台账：

- **订阅台账**：周期扣费的东西集中在一张表里——VPS、域名、香港手机号、OpenCode Go、88VIP、三张电话卡，每条都带扣费日、提前提醒量，以及滴答清单里的对应任务 ID；规则是“新增订阅 → 账本记一笔 → 加一行 → 建提醒”，“取消订阅”则删任务、移表、记最后一期。
- **耗材台账**：能摊销的东西单独记，核心是“日均成本”。比如剃须刀片 ¥84（11 月 9 日买的）、维生素片 ¥135（11 月 13 日买的），下次再买同款时回来看一眼用了多少天、日均多少，就知道该买贵点的还是便宜点的。

这两张表最后被渲染成一个静态页面（Wallos 风格深色主题），推到 GitHub Pages。推之前先跑校验，**账不配平就不发布**——省得把错的数字挂在网上。

还有个细节：账本里凡手机号、卡号一律打码（写 `5709 ****`），滴答清单里的任务可以留完整信息，仓库里的账本不行。

## 播客流水线：从 Codespace 搬回自己的机器

[bilibili-to-podcast](https://github.com/TangMisaka23001/bilibili-to-podcast) 这个项目之前跑在 GitHub Codespace 上，核时用完了，流水线就断了。这次干脆整体搬到服务器上，让 dsh 定时驱动。

流水线本身是一条七段的链：`prune → fetch → summarize → rss → gen-index → sync → size`，抓 B 站合集、抽音频、生成 RSS、镜像到对象存储、再生成订阅首页。现在订阅了十几个合集，推理、读书、经济分析都有，首页在 podcast.misakatang.xyz。

每周日凌晨 03:00，定时任务跑一遍 `tools/weekly_run.py`，它会快照 RSS、跑流水线、再快照一次做 diff，最后吐一段 JSON 出来，里面有成功与否、耗时、日志路径、RSS 变化，以及三个问题列表：疑似 cookie 过期、疑似网络故障、疑似代码缺陷。

这套设计里最关键的一点是**让 AI 别乱改代码**：cookie 过期（`code: -101`、sessdata 失效）是凭据问题，只能等我换 cookie；网络抖动是外部环境问题，下次跑就恢复；只有出现 traceback 才叫代码问题，而且必须改完跑 `pytest -q` 全绿、再重跑一次完整流水线确认 exit code 变 0。判断原则写死在提示词里——**拿不准的时候优先归类成前两种不改，误改代码的代价远大于漏修一次。**

跑完的总结直接推到 QQ：每个 feed 新增/删除/变更了几集、标题是什么，哪天没变化就一句“本次无变化”。

## 炼化 E 大：645 篇文章变成一个静态知识库

另一件费事的事是把长赢指数投资计划主理人 E 大在且慢社区发的所有图文帖“炼化”一遍。

产出的仓库是 [qieman-finance](https://github.com/TangMisaka23001/qieman-finance)：抓了 **645 篇文章**（2025-10-22 到 2026-11-10），再用 LLM 把每篇抽成结构化信息——一句话核心思想、要点、作者本人观点、数据点、涉及的指数基金实体、标签、值不值得深读、可执行动作，再打上 8 类内容标签。

这一步的原始工具是 GitHub 上 `chubbyguan/chubbyskills` 的 `content-enrich`（MIT 协议），但它是 Python 写的，这台机器没有 Python，所以用 Node 复刻了一遍链路并扩了字段。

抓取和抽取阶段踩的坑后来都写进了仓库文档，摘几条最值钱的：

1. **评论区必须解析**。原来的正则有两个 bug：多行评论被截成首行、「回复 @xxx」格式整段丢失，结果 56665 那篇的持仓明细表直接消失。改成“先定位所有评论头、再按位置切片正文”之后，评论覆盖 1361/1361 = 100%。
2. **`max_tokens` 必须 ≥ 12000**。模型的 `reasoning_content` 会吃光 token 预算，`max_tokens=4000` 时 finish=length 导致空响应，三次只成功一次；调到 12000 之后三次全中，而且更快。
3. **主题聚类不能用 LLM 自由标签**。让它自由打标会得到 223 种 domain，相似度聚类直接塌成一簇 600 篇。最后改成 21 个人工规范化的主题 + 关键词打分，互斥且 100% 覆盖 645 篇。

产物最后用 Quartz v4.5.2 拼成一个中文知识库站点：645 篇原文、645 篇摘要、三份报告，push 到 `main` 就自动构建部署。质量验收是 24 项全过，其中**数值保真率 99.0%**（3925/3965 个抽取出来的数字能回溯到原文，没命中的逐一核查过，都是 `2.26` 写成 `2.26%` 这类格式差异）。

总纲那段话我抄在这儿自己看：把普通人的投资从预测行情、追逐暴利，转向以守住本金、现金流和长期购买力为先——先盘点资产、负债、支出与风险承受力，再构建核心—卫星组合。

## 踩坑清单

1. **定时触发的回合没有 IM 投递消费者**。`dsh_im_return_file` 会直接报 `Error: No active IM delivery consumer owns this turn. The file was not queued.`；微信侧还会出现 `[dsh-im] Session text was not delivered [unbound] session=...`，任务准时触发但文本凭空消失。正确做法是主动调 `push.mjs` 推；要发图片只能走 `qq-image.mjs` 直发 QQ Bot API。
2. **流水线阶段别用 `&&` 串联**。原先 cookie 一过期，summarize 退出 1，后面的 rss / gen-index / sync 全都不跑——代码明明是好的，播客却停止更新。改成各阶段独立执行、统一汇总退出码，单个阶段失败不再掐断整条链。
3. **消息渠道的能力不对等**。微信主动推送只支持文字，文件图片走 QQ；微信 bot 的登录会话还会过期（报 `-14 session timeout`），过期后得重新扫码。定时任务要发图就别指望微信。
4. **账本里的敏感信息一律脱敏**。手机号打码是硬规矩，滴答任务可以留全，仓库里不行——仓库是要公开的。
5. **凭据迁移容易丢字段**。`.credentials.yaml` 换格式时丢过一个 key，导致额度播报静默失败一天。取值命令要同时兼容新旧两种格式，拿不到就直接播报“凭据缺失”，别发空请求。

## 结尾

这台 60 美元的小机器现在跑的东西，比刚搬过去那会儿多了一层意思：它不只托管静态服务，还成了我日常的入口。

说到底也没做什么惊天动地的事——消息还是我发的，决定还是我做的。但“记下来”“到点提醒我”“这个月花了多少”“顺便把账提交上去”这些原本靠脑子的活儿，现在有人（或者说有台机器）接着了。

省下来的注意力，比省下来的时间值钱。
